# 回滚手册

## 允许的回滚目标

白名单启用后，只能回滚到理解 `public/allowlist`、不会无条件应用广播、且能保持版本序号水位的兼容基线。禁止回滚到重构前二进制。

## 步骤

1. 关闭请求入口并停止全部服务实例，确认在途事务结束或运行中租约过期；项目不再提供任务暂停环境变量。
2. 保存任务、执行记录和审计快照，确认是否有未完成的白名单变更。
3. 部署兼容回滚版本；保留应用登记、版本 UUID、范围、名单、任务、审计及所有旧列。
4. 不回退 `AUTO_INCREMENT`，不重编号，不覆盖已发布包 URL。
5. 在隔离环境先验证回滚版本会重新读取当前策略，而不是发送任务创建时的旧快照，再恢复服务；启动后 Worker 自动领取及恢复任务。

数据库迁移不做破坏性 down。本版已退役管理员账号/会话并统一消息表；只可回滚到支持 API Key 与 ota_messages 的版本。恢复旧认证或旧消息结构需要升级前完整备份及匹配二进制，退役迁移会主动拒绝自动 down，不能指望重新创建空表恢复账号。

代码回滚与包内容回滚不同。若客户端需要恢复旧内容，应把已验证内容作为更大的新版本 ID 重新发布。

## 正式字段读取切换回退

若问题局限于新目录映射，可先停止该应用所有写入口及推送，保留数据库和账本快照，再由 DBA 在事务中将**已确认的单个应用映射**的 `read_model` 改回 `compatible`、递增 `catalog_revision`。不要更改 ID 水位、清空正式列、降低 schema version 或删除迁移进度。重新部署/重启理解新旧双写及发布范围的兼容版本，清空目录缓存并验证后恢复流量。

`compatible` 仍优先读取已有正式值，仅允许缺失值回退；它不是恢复损坏数据的手段。若已存在正式/旧列冲突，应先依据快照核实并修复，不能把切换模型当作数据恢复。`failed/paused/running` 迁移必须从原账本恢复并完成对账，不能直接手工标记 `ready`。

新增应用迁移账本的 `down()` 主动拒绝删除进度。MySQL 补列 DDL 不随数据批次回滚，恢复旧结构只能另行评估受控变更；兼容期不删除列。
