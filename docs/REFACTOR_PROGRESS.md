## 优先缺陷与补齐顺序

### F1：启停接口未同步正式启用列（已修复）

[setEnabled()](../src/releases/release-management.service.ts) 原来只写 `enable`，而 [mapStoredReleaseRecord()](../src/releases/release-record.mapper.ts) 优先读 `is_enabled`。现已在同一事务双写两列。

`5cdf2cd` 增加回归：管理策略写入 → mapper → HTTP 共用查询服务/Gateway；验证停用后的检查、订阅补发、实时撤销、重新启用，以及事务失败时不失效缓存、不分发。数据库执行为替身，未替代真实 MySQL 回滚验收。

### F2：取消应用订阅后重订阅复用 revision（已修复）

[subscribeApplication()](../src/realtime/subscriptions/connection-subscription.store.ts) 原来根据当前 Map 项分配 revision；取消订阅后重建会复用 1。`4c16709` 改为连接生命周期单调计数，身份变化也从同一计数器分配修订；重连仍通过 generation 隔离。

修复前直接调用真实 Store 的复现结果（保留历史证据）：

```json

  "oldSubscriptionRevision": 1,
  "newSubscriptionRevision": 1,
  "oldSubscriptionAcceptedAsCurrent": true
```

修复后的 Store 回归拒绝旧快照；Gateway 延迟 Promise 回归验证取消→换平台→重订阅后只发送新平台结果，旧结果不会撤销或覆盖新结果。

### F3：目录缓存不能证明同一修订（已修复，待真实 MySQL 验收）

[loadCatalogFromDatabase()](../src/updates/catalog/release-catalog.service.ts) 现使用同一连接的 `REPEATABLE READ` 事务读取应用表映射、`catalog_revision`、版本与名单。目录直接使用登记表名；缺少旧应用登记时使用修订 0，不再借用单个发布的策略修订。

`de4a7b9` 隔离失效/强制刷新前的在途加载，旧调用方采用新快照且不能回填缓存；草稿发布提交后失效缓存。任务将 effectiveRevision 传给分发，快照不匹配则重试；批次开始、结束（含零目标）检查租约与当前目录修订。新增目录、Gateway 和 Worker 回归，实际 MySQL 存储引擎、隔离及竞争仍需条目 45 验收。

### F4：历史迁移工具已交付，存储边界仍待拆分

`migrate:app` 默认只读预演；实际执行要求确认数据库、备份、停写和历史 ID 水位。迁移按应用+版本持久化进度；每批锁行后校验，新字段与断点同事务提交，DDL 单独恢复。旧列冲突、混合应用、非法元数据、异常历史计数和续跑间数据变化均阻止执行，不覆盖或猜测。完成对账后才能显式选择正式目录映射，默认保留 compatible。

`058cd77` 修复登记前缀再次替换数字的问题，覆盖工厂与旧查询/写入路径。prepare 不再对已就绪应用重复 DDL，不会把异常历史错误次数改成 1；历史上报回填统一交给迁移工具。迁移、准备使用同一互斥锁，失败竞争不修改另一进程的状态。

迁移行解释、发布/启停双写已归入 `compat/legacy/persistence/`，正式服务使用 `ReleaseWriteRepository`；调度、审计和账本归入 `infrastructure/migrations/`。`withApplicationWrite()` 统一旧/v2 发布和已发布策略的事务锁，并在锁内重新确认 ready 与前缀；旧发布不再重复建表。读取/其他写入端口、名单及真实 HTTP/WebSocket 全链路影子对账仍缺，不能因此移除旧列兼容。

本轮已修正身份认证装配：根模块和独立管理员模块显式引入 `AuthModule`，测试不加载 `LegacyCompatibilityModule` 仍能拒绝无效凭证、校验管理员账户。该项解耦不代表存储与迁移边界已经完成。
