## 优先缺陷与补齐顺序

### F1：启停接口未同步正式启用列

[setEnabled()](../src/releases/release-management.service.ts) 只写 `enable`，而 [mapStoredReleaseRecord()](../src/releases/release-record.mapper.ts) 优先读 `is_enabled`。新发布会同时写两列，因此停用后可能仍被判定启用，禁用发布也可能无法重新启用。

本次只读复现：把 `{ is_enabled: 1, enable: 0 }` 交给真实 mapper，输出 `enabled: true`。需统一策略双写，并覆盖停用后 HTTP、补发、实时撤销和重新启用的回归。

### F2：取消应用订阅后重订阅复用 revision

[subscribeApplication()](../src/realtime/subscriptions/connection-subscription.store.ts) 根据当前 Map 项分配 revision；取消订阅删除该项，再订阅又得到 1。同一连接 generation 未变，旧异步查询的 revision=1 被 `isCurrent()` 接受。

本次直接调用真实 Store 复现结果：

```json
{
  "oldSubscriptionRevision": 1,
  "newSubscriptionRevision": 1,
  "oldSubscriptionAcceptedAsCurrent": true
}
```

需使用不因取消订阅复位的修订计数，并覆盖取消→换上下文→重订阅期间的异步查询。

### F3：目录缓存不能证明同一修订

[loadCatalogFromDatabase()](../src/api/version/ota-version-query.service.ts) 分别读取版本和名单，没有一致性事务。它取各发布 `policyRevision` 最大值，无法表示应用级 `catalog_revision`。`invalidate()` 只删除缓存，`force=true` 仍可复用失效前的在途加载。

需将应用修订、版本和名单绑定到一致快照；失效后不得采用旧加载结果；任务执行记录的 effectiveRevision 必须与实际分发快照一致。

### F4：存储和迁移仍依赖旧实现

版本 prepare 没有完成正式历史字段回填；不存在干跑、分批、断点账本、影子对账和正式读取切换。发布双写仍在多个服务中展开。先建立 Repository 边界，再提供按应用迁移工具和真实 MySQL 验证，才能移除旧列兼容。

另外，`AuthModule` 目前只由 `api/admin/admin.module.ts` 引入；移除 `LegacyCompatibilityModule` 将连带移除全局 `APP_GUARD`。正式身份认证必须独立装配，不能只凭直接 import 搜索声称兼容层已经可以删除。

### F5：任务审计与管理能力未闭环

运行中计数只在内存累计、结束时落库；跳过原因和逐版本摘要列尚未填充。失败操作审计、完整名单差异、管理操作幂等、名单分页、时间范围查询和已发布元数据编辑还需实现。相关字段或路由存在不能计为行为已经完成。

建议顺序：先修 F1/F2/F3 并加回归，再补 F4 的迁移和存储边界，随后补 F5，最后执行真实端到端/MySQL/压测与目标环境演练。外部 SDK/业务项目可以按契约协同推进。

以上缺陷在本轮仍为待修复项；本轮变更是核对、结构拆分和文档纠正，不把目录移动记成功能修复。
